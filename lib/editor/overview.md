# lib/editor 개요

퀴즈 편집기와 설문 편집기가 함께 쓰는 계층입니다. 두 편집기는 다루는 도메인이 다르지만 "문서 하나를 통째로 들고 있다가 통째로 저장하는" 모양이 같아서, 그 모양에서만 나오는 문제들을 여기 모았습니다.

원래는 전부 `components/quiz/quiz-editor.tsx` 안에 있었습니다(그 파일 하나가 1439줄이었습니다). 설문 편집기를 만들면서 복사하는 대신 끌어올렸고, 퀴즈 편집기도 이쪽을 쓰도록 바꿨습니다 — 복사해 두면 한쪽에서 고친 버그가 다른 쪽에 남습니다.

## `use-document-save.ts`

`useDocumentSave({ onSave })`. 저장 요청 자체는 호출자가 만들고, 여기서는 매번 똑같이 필요하고 매번 똑같이 틀리기 쉬운 네 가지를 맡습니다.

1. **덮어쓰기 방지.** 저장 요청이 도는 동안 사용자가 계속 타이핑하면, 돌아온 서버 응답을 그대로 화면에 넣는 순간 그 사이의 편집이 사라집니다. 편집마다 번호를 올려 두고 `context.isCurrent()`로 확인한 뒤에만 응답을 반영합니다. **호출자가 이 검사를 빼먹으면 그대로 버그가 됩니다** — 그래서 콜백 인자로 넘겨 눈에 띄게 했습니다.
2. **동시 저장 방지.** 자동 저장 타이머와 Ctrl+S가 겹치면 같은 문서가 두 번 날아갑니다.
3. **자동 저장.** 30초마다, 바뀐 게 있고 저장 중이 아닐 때만.
4. **나가기 경고.** 저장 안 한 변경이 있으면 새로고침·닫기를 막습니다.

콜백은 ref로 붙잡습니다. 타이머와 keydown 리스너는 한 번만 등록하는데 그 안에서 부르는 저장 함수는 매 렌더의 최신 상태를 봐야 하기 때문입니다.

`dirty`가 내려가는 것은 `onSave`가 true를 돌려주고 **그 사이 편집이 없었을 때뿐**입니다. 저장 도중 편집한 것을 "저장됨"으로 표시하면 사용자가 그대로 창을 닫습니다.

발행·삭제처럼 저장이 아닌 요청은 이 훅이 관여하지 않습니다. 호출자가 자체 `busy` 상태를 두고 `saving || busy`로 합쳐 화면에 씁니다.

`useFlash`도 같은 파일에 있습니다 — 잠깐 떴다 사라지는 안내 문구인데, 타이머를 정리하지 않으면 사라진 컴포넌트에 setState가 걸립니다.

## `use-list-drag.ts`

끌어서 순서 바꾸기. 퀴즈의 문제 썸네일 레일(가로·세로)과 설문의 질문 카드 목록(세로)이 같은 훅을 씁니다.

HTML5 Drag and Drop을 쓰지 않은 이유 — 터치에서 아예 동작하지 않고, 목록 가장자리 자동 스크롤을 넣을 방법이 없습니다. 둘 다 이 화면들에서는 없으면 안 됩니다. `@dnd-kit`도 의존성에 있지만(패드 보드가 씁니다) 요구가 달라 여기서는 쓰지 않습니다 — 이 훅은 "끌어서 순서만 바꾸기"에 필요한 것만 담아 훨씬 작습니다.

까다로운 지점 셋:

- **마우스와 터치의 시작 조건이 다릅니다.** 마우스는 6px 움직이면 바로, 터치는 280ms 길게 누른 뒤에만 시작합니다. 터치에서 즉시 시작하면 목록을 스크롤하려는 손짓이 전부 드래그가 됩니다.
- **목록이 스크롤돼도 카드가 손가락을 따라와야 합니다.** 매 프레임 스크롤 변화량을 보정합니다.
- **드래그가 끝나면 브라우저가 click을 한 번 더 보냅니다.** 그대로 두면 "놓은 자리의 항목이 선택됨"으로 오작동해서, `suppressClickAfterDrag`가 캡처 단계에서 한 번 삼킵니다.

## `list-ops.ts`

`moveItem`·`insertAfter`·`removeAt`·`replaceAt`·`selectionAfterRemoval`. 전부 새 배열을 돌려주고 원본을 건드리지 않습니다(React 상태로 그대로 넣기 위해서입니다).

별것 아닌 splice지만 두 편집기가 각자 인라인으로 쓰면 "복제는 뒤에, 삽입도 뒤에, 삭제 후 선택은 앞으로" 같은 규칙이 조금씩 어긋납니다. 특히 `selectionAfterRemoval`은 목록 끝에서 빈 곳을 가리키기 쉬운 계산이라 한곳에 둡니다.
