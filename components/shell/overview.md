# 앱 셸 개요

로그인 전용 대시보드의 데스크톱 고정 사이드바와 모바일·태블릿 드로어 내비게이션을 담당합니다. 공개 홈페이지(`/`)와 패드 본문(`/b/[slug]`)에는 이 셸을 그리지 않습니다.

- `app-sidebar.tsx`: 메뉴, 교과목 바로가기, 폴더, 최근 방문을 그리는 Client Component입니다. 960px 이상은 상단바 62px를 뺀 고정 높이 사이드바, 그 아래는 왼쪽 아래 버튼으로 여닫는 `100dvh` 드로어입니다. 이 내용만 `.app-sidebar-scroll`에서 스크롤합니다. **정적 메뉴 항목·라벨·아이콘·필요 권한은 여기에 적지 않고 `lib/routes.ts`의 매니페스트가 선언합니다** — 이 컴포넌트는 서버가 권한 필터를 끝낸 메뉴를 그리기만 합니다. 교과목 이름은 대시보드·교과목 영역, 폴더와 실제 최근 방문 6개는 패드·퀴즈·설문 영역에 들어왔을 때만 `/api/navigation/sidebar?section=...`에서 지연 조회합니다. 네 응답은 같은 `useSidebarData`가 요청 취소·늦은 응답 무시·변경 이벤트 갱신을 담당합니다.
- `sidebar-account-dock.tsx`: 서버가 이미 확인한 사용자와 관리자 접근 권한으로 프로필 카드·관리자 링크를 렌더링해 `AppSidebar`의 하단 슬롯으로 전달합니다. 테마 전환과 로그아웃은 브라우저 상태·클릭 처리가 필요하므로 해당 버튼만 Client Component입니다. 도크는 스크롤 영역 밖에 있어 메뉴 길이와 무관하게 항상 화면 하단에 남습니다.
- `nav-icons.tsx`: 매니페스트의 아이콘 문자열 키를 lucide 컴포넌트로 잇습니다. `lib/routes.ts`는 `proxy.ts`(Node 런타임)에서도 평가되어 React·lucide를 가져올 수 없으므로 매핑을 여기로 분리했습니다.
- `nav-counts.tsx`: 하위 항목의 개수 배지를 **화면 → 셸**로 올리는 컨텍스트입니다. 집계를 가진 화면이 `usePublishNavCounts(...)`로 올리고 사이드바가 `useNavCounts()`로 읽습니다. 자세한 이유는 아래 "개수 배지" 절.
- `app-shell.tsx`: 본문과 `AppSidebar`를 나란히 렌더링합니다. `showSidebar={false}`인 패드 캔버스에서는 고정 사이드바와 모바일 열기 버튼을 모두 생략합니다.
- `dashboard-chrome.tsx`: `AppShell`, 상단 알림과 개수 배지 Provider를 묶어 `app/(workspace)/layout.tsx`에 상주시킵니다. 패드 생성 Provider는 `/pad` 페이지에만 있고, 셸의 작은 로그아웃 버튼은 로그인 폼·모달 Provider와 분리돼 있습니다.

상주 브랜드·`TopNav`·`AppSidebar`·계정 독의 링크는 `prefetch={false}`입니다. 이 링크들은 첫 화면부터 모두 뷰포트에 있어 Next 기본 prefetch를 두면 현재 경로와 무관한 pad·quiz·forms·admin 라우트의 RSC와 청크가 동시에 내려올 수 있습니다. 클릭한 경로만 가져오도록 해 초기 네트워크 경쟁을 막습니다. 교과목은 퀴즈·패드·학생을 묶는 수업 기준이므로 상단 탭을 따로 차지하지 않고 대시보드 사이드바에 둡니다. `/courses/*` 주소는 유지하지만 `TopSection.prefixes`가 이 경로도 대시보드 영역으로 판정합니다.

## 하위 항목과 개수 배지

매니페스트의 `nav.parent`가 채워진 항목은 부모 아래에 들여쓴 하위 항목으로 그립니다(`.app-sidebar-subnav`). 부모는 자기 자신이 활성이거나 하위 항목 중 하나가 활성이면 함께 강조합니다 — 접히지 않고 항상 펼쳐 두므로, 부모만 꺼져 있으면 지금 어느 묶음에 있는지 읽히지 않습니다. 부모가 권한으로 걸러지면 하위 항목도 함께 사라집니다.

하위 항목은 `/report/pads`처럼 모두 실제 경로입니다. 퀴즈·설문은 패드 구조에 맞춰 평면 메뉴로 바꾸고 할당·발행·응답 상태를 본문 필터로 옮겼습니다. 사이드바는 `useSearchParams()`를 구독하지 않고 `usePathname()`만으로 활성 항목을 계산하므로 검색어·정렬·페이지 번호가 바뀔 때마다 상주 셸까지 다시 렌더링되지 않습니다.

개수 배지(`nav.countKey`)는 **집계를 이미 가진 화면이 올려 줍니다.** 셸이 직접 조회하지 않는 이유는 두 가지입니다. ① App Router는 같은 레이아웃을 공유하는 페이지끼리 이동할 때 레이아웃을 다시 렌더링하지 않으므로, 레이아웃에서 조회하면 패드만 쓰는 사람에게도 퀴즈 집계가 돌고 즐겨찾기를 껐다 켜도 배지가 굳습니다. ② 전용 엔드포인트를 사이드바가 부르면 같은 수를 위해 DB를 한 번 더 왕복하고, 화면의 목록과 배지가 서로 다른 시점을 가리킬 수 있습니다. 화면이 마운트되지 않으면 값이 비므로 "그 섹션이 아닐 때는 조회하지 않는다"가 구조적으로 지켜집니다. 값이 아직 없는 키는 배지를 그리지 않습니다 — 0으로 대신 그리면 "없다"는 거짓말이 됩니다.

## 영속 레이아웃

`app/(workspace)/layout.tsx`는 `/dashboard`, `/pad/*`, `/quiz/*`, `/forms/*`, `/report/*`, `/profile`을 공유합니다. 로그인 사용자는 한 번 그린 `DashboardChrome` 안에서 `page.tsx` 본문만 교체되므로, 라우트를 옮겨도 사이드바 DOM과 알림 SSE가 다시 마운트되지 않습니다. 퀴즈 보관함, 설문 상태 목록, 활동 종류별 리포트는 그 아래에 route-group layout을 한 단계 더 두어 제품 안의 공통 프레임도 유지합니다. 비로그인 상태에서는 셸 없이 `children`만 반환하고 각 보호 페이지가 로그인 화면으로 이동시킵니다.

레이아웃은 `getCurrentUser`와 읽지 않은 알림 개수(`getNotificationSummary`)만 읽습니다. 패드 홈·교과목·템플릿·접근 요청은 각 기능 페이지에서만 조회합니다. 대시보드 사이드바의 교과목 바로가기도 해당 영역 진입 후 이름·링크만 최대 100개 읽고, 퀴즈·설문은 접근 가능한 실제 최근 방문 제목·링크만 6개 읽습니다. 학생 수·문항 수·응답 수 같은 본문 집계는 이 API가 조회하지 않습니다. 알림 20개의 관련 패드·글·퀴즈·설문 제목도 벨을 처음 열 때 `/api/notifications`가 지연 조회합니다. 따라서 다른 영역 진입이 사용하지 않는 보관함 전체 조회를 기다리지 않습니다.

사이드바는 영속하므로 활성 항목을 서버 prop으로 고정하지 않고 `usePathname()`으로 계산합니다. 판정 규칙(정확히 일치 / 하위 경로 포함)은 매니페스트의 `match`가 정하고 `isActive()`가 적용합니다. `/dashboard`만 “내 패드”를 활성화하며 공개 루트 `/`는 이 라우트 그룹 밖입니다. 브랜드 링크도 셸 안에서는 `/dashboard`로 이동합니다.

메뉴 노출 판정(`navSectionsFor`)은 **메뉴를 숨기는 용도일 뿐**입니다. 실제 접근 경계는 각 페이지와 API가 다시 검사하므로, 매니페스트에 권한을 잘못 적어도 데이터가 새지는 않고 메뉴만 어긋납니다.

모바일 드로어가 열리면 배경 스크롤을 잠그고 Escape, 배경, 닫기 버튼, 링크 선택으로 닫습니다. `/b/[slug]`는 `showSidebar={false}`를 사용하므로 모바일에서도 사이드바 버튼이 나타나지 않습니다.

패드·퀴즈·설문의 최근 방문은 각각 `BoardVisit`·`QuizVisit`·`FormVisit.lastVisitedAt` 최신순 최대 6개입니다. 읽기 권한을 통과한 콘텐츠 진입만 기록하며 수정 시각과 활동 알림용 `BoardFollow`에는 영향을 받지 않습니다.
