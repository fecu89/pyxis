# Pad 사진 업로드와 백그라운드 변환

## 동작

`PAD_BACKGROUND_IMAGES_ENABLED=true`이면 Pad 게시물 사진은 파일 수신·검증·메타데이터
정리가 끝나면 첨부로 저장하고 게시를 완료합니다. WebP(최대 2560px)와 썸네일(960px)은
나중에 생성합니다. 파일 전송·권한 검증·DB 저장 시간은 여전히 필요합니다.

- 초기 제공: JPEG/PNG/WebP의 압축 픽셀을 보존하면서 EXIF/XMP/IPTC/텍스트 정보를 제거합니다.
  JPEG는 방향 값만 새 최소 EXIF에 기록합니다. 표시용 ICC 정보는 유지합니다.
- 예외: GIF·애니메이션·방향 보정이 필요한 PNG/WebP는 기존 동기 재인코딩을 사용합니다.
  지원하지 않는 실제 형식이나 손상된 컨테이너는 원시 바이트를 공개하지 않고 거절합니다.
- 기존 파일 크기·픽셀·권한·손님 5개/회원 20개 제한은 유지합니다.
- 다른 업로드(댓글·프로필·퀴즈·설문·배경)는 기존 방식 그대로입니다.

## 작업과 삭제

Attachment 생성과 ImageProcessingJob 등록은 같은 트랜잭션입니다. 실행기는 서버에서
2초마다 확인하며 한 번에 한 작업을 실행합니다. 기존 Sharp 처리 게이트도 공유합니다.
단일 서버 배포를 전제로 하며 별도 Redis/워커 서비스는 필요하지 않습니다.

작업 상태는 `PENDING → PROCESSING → CLEANUP_PENDING → DONE`입니다. 변환 실패는
5초·30초·2분·10분 간격으로 재시도하고 5회 시도 후 `FAILED`로 남깁니다. 변환 실패 시
초기 사진은 계속 제공됩니다. 임대는 2분이며 20초마다 갱신합니다. 만료된 실행기는 결과를
반영할 수 없고 재시작 시 다른 실행기가 작업을 회수합니다.

두 출력 파일을 완성한 뒤 DB 참조를 교체합니다. 주소 `/f/첨부ID`는 바뀌지 않으며 화면은
imageRevision 이벤트로 새 이미지를 다시 읽습니다. 원본은 교체 후 최소 60초 뒤 정리합니다.
파일을 이미 읽는 요청은 열린 파일 핸들로 계속 처리하며, 과거 경로가 사라진 요청은 최신
경로와 권한을 한 번 다시 확인합니다. 파일 삭제 실패는 변환과 별개로 재시도합니다.

삭제된 첨부는 재생성하지 않습니다. 작업 기록은 첨부 cascade 삭제에 함께 지워지지 않아
남은 파일을 회수할 수 있습니다. `pending-*`, `optimized-*` 중 1시간 이상 된 미참조 파일을
업로드 루트 아래에서만 정리합니다. 심볼릭 링크를 따라가지 않습니다.

변환 완료 알림은 파일 교체가 커밋된 뒤 짧은 행 잠금 안에서 발행합니다. 삭제가 먼저
확정되면 알림을 보내지 않고, 알림이 먼저라면 삭제 알림보다 앞서 전달합니다. 상세 화면도
저장 응답보다 먼저 온 완료 정보를 받아 같은 첨부의 높은 revision을 유지합니다.

## 운영 적용

1. 파일·DB 백업 상태를 확인합니다.
2. 마이그레이션 `20260922010000_pad_image_jobs`를 포함한 미적용 마이그레이션을 먼저 적용합니다.
3. 새 앱을 빌드·배포합니다. 새 서버의 주기 작업이 있어야 하므로 반드시 기존 `server.ts` 시작
   방식을 사용합니다. Next 단독 서버만 실행하면 변환 작업이 처리되지 않습니다.
4. 환경 설정 `PAD_BACKGROUND_IMAGES_ENABLED=true`를 적용하고 프로세스를 재시작합니다.
5. 작은 사진을 올려 게시 완료, 나중의 MIME/revision 전환, 원본 정리를 확인합니다.

운영 DB 마이그레이션·설정 변경·배포는 구현과 별도로 승인받아 수행합니다.
기본값은 false이며 **코드만 배포해도 자동 활성화되지는 않습니다.**

### 운영 적용 기록 — 2026-09-27

사용자 승인 후 DB 백업을 생성하고 `20260922000000_signup_consent`와
`20260922010000_pad_image_jobs`를 적용했습니다. 미적용 마이그레이션은 없습니다.
운영 `.env`와 재시작 프로세스에 `PAD_BACKGROUND_IMAGES_ENABLED=true`를 반영하고
`yarn deploy`로 새 빌드에 전환했습니다. 내부 홈·로그인·새 빌드 정적 파일과 외부 홈의
HTTP 200, 실행 프로세스의 활성화 값, 전환 후 새 오류 로그 없음까지 확인했습니다.
실제 사용자 게시물을 생성하는 운영 업로드 테스트는 수행하지 않았습니다.

### 롤백

먼저 설정을 false로 바꾸면 새 업로드는 기존 동기 처리로 돌아갑니다. 작업 실행도 멈추지만
이미 받은 초기 사진은 계속 읽을 수 있고 DB 작업은 남습니다. 다시 true로 켜면 재개합니다.
추가형 스키마를 먼저 삭제하지 않습니다. 이전 앱은 작업 처리를 하지 않으므로 큐가 남은
동안 예전 앱에서 사진 삭제·복사를 진행하기보다는 새 앱의 설정 OFF 방식으로 되돌립니다.

### 모니터링과 복구

- 비완료 작업은 최대 256개이며 FAILED와 정리 대기도 포함합니다. 초과 시 새 비동기 사진
  업로드를 503/Retry-After: 5로 거절하고 화면의 기존 재시도 UI를 사용합니다.
- 상태별 작업 수, 가장 오래된 availableAt, FAILED 수, 디스크 여유 공간을 확인합니다.
- `[pad-image] conversion-retry`, `cleanup-retry`, `worker-retry`를 확인합니다.
  로그에는 파일 내용·EXIF·원래 이름·환경변수 값을 기록하지 않습니다.
- FAILED 재시도는 원인(손상 파일/용량/디스크 권한)을 먼저 확인한 뒤 **대상 job ID만** 골라
  status=PENDING, attempts=0, availableAt=현재, leaseToken/leaseExpiresAt=null로 갱신합니다.
  inputPath와 기존 출력·정리 경로는 보존합니다. 임의 SQL로 전체 큐를 초기화하지 않습니다.
- 정리 실패는 CLEANUP_PENDING 상태로 남아 자동 재시도합니다. 파일이 사라졌더라도 ENOENT는
  정상 정리로 처리합니다. 이미 참조되는 최신 이미지 경로를 수동으로 삭제하지 않습니다.

## 검증

`yarn verify:pad-images`는 메타데이터/방향, 실제 파일 교체, 실제 PostgreSQL 임대·재시도·용량,
30건 동시 업로드 요청, 삭제 경합, 파일 스트리밍, 브라우저의 실제 작성기와 이미지 갱신을 검증합니다.
합성 GPS IFD와 비대칭 픽셀 fixture로 JPEG 방향 1–8·ICC 유지·개인 메타데이터 제거를 확인합니다.
실제 ZIP 생성과 경로 교체 시 복사 helper도 검증합니다. 파일 제공 라우트의 승인 대기
작성자/관리자 허용, 비회원/다른 사용자 거절, 권한 회수, Range/304를 검사합니다.

검증 한계: 인증 서비스는 fixture로 대체했으며 실제 계정·운영 부하 테스트는 하지 않았습니다.
실제 `cloneBoard` 전체 트랜잭션과 이미지 교체의 동시 실행, 전체 상세 페이지의 이벤트 역전
브라우저 테스트는 아직 없습니다(복사 helper와 상세 화면이 사용하는 revision 병합 함수는 검증).
브라우저 테스트의 API/변환 완료 이벤트는 fixture이며, 별도의 서버 테스트가 실제 파일·DB를 사용합니다.

통합 테스트는 명시적인 `TEST_IMAGE_DATABASE_URL`이 필요합니다. 데이터베이스 이름은
`pad_images`, Unix socket 디렉터리는 `/tmp/pyxis-image-pg.*`여야 합니다. 일반 DATABASE_URL이나
프로젝트 `.env`를 사용하지 않습니다. **테스트 데이터베이스의 작업 행을 정리하는 테스트이므로
반드시 임시로 새로 만든 전용 PostgreSQL만 연결합니다.** Playwright는 로컬 설치 또는
`PLAYWRIGHT_MODULE_PATH`로 지정합니다.

## 구현 판단

- 드문 방향 보정 PNG/WebP와 애니메이션은 안전성을 위해 동기 경로를 유지하므로 대기가 남습니다.
- 백그라운드 변환은 한 번에 하나로 제한했습니다. 게시 요청과 자원을 나누지만 최적화 큐는
  여러 개를 동시에 처리할 때보다 천천히 줄어듭니다.
- 다른 업로드에 영향을 줄이지 않도록 기존 동기 인코더를 유지했습니다. 두 인코더의 변환
  설정은 동일하며 향후 설정 변경 시 함께 관리해야 합니다.
- 완료 이벤트에 공개 가능한 전체 첨부와 이미지 속성 패치를 함께 실었습니다. 먼저 온 완료
  이벤트를 수용하면서 기존 설명은 보존하지만 이벤트 크기가 조금 늘어납니다.
- 현재 폴더의 미커밋 변경으로 보관하며 자동 커밋·푸시는 하지 않습니다.

컨테이너 검증 참고: [W3C PNG 명세](https://www.w3.org/TR/png/),
[Google WebP 컨테이너 명세](https://developers.google.com/speed/webp/docs/riff_container).
