# Pad 사진 업로드: 게시 완료와 이미지 최적화 분리

작성일: 2026-09-22
상태: 사용자 검토용 설계. 구현·운영 DB 변경·배포 전.

## 1. 목적과 범위

사용자 요구는 여러 사람이 사진을 올릴 때 이미지 변환 대기 때문에 글쓰기 화면이
계속 ‘게시 중’으로 남는 문제를 줄이는 것이다. 서버에 파일이 안전하게 저장되면
기존 게시 절차를 완료하고, WebP 및 썸네일 생성은 이후 진행한다.

- 이번 대상: Pad 게시물의 새 이미지 첨부(로그인 사용자 및 기존 허용된 손님).
- 댓글·프로필·퀴즈·설문·보드 배경의 업로드 방식과 기존 이미지의 일괄 변환은 제외한다.
- 파일 전송, 보안 검증, DB 저장 시간까지 없애는 것은 아니다.
- 기존 승인 대기, 접근 권한, 업로드 정책, 게시물당 첨부 제한은 그대로 유지한다.
- ‘원본 우선’은 미검증 원시 바이트를 즉시 공개한다는 의미가 아니다.

## 2. 확인한 현재 구조

- `post-composer.tsx`는 글 저장 후 `queue.start(postId)`를 기다리고 마지막 PATCH 후 닫힌다.
- 클라이언트는 최대 3개씩 업로드하지만 서버 이미지 변환 게이트는 기본 2개다.
- `store-upload.ts`는 원본 수신 후 WebP 본문과 썸네일을 모두 생성해야 반환한다.
- 첨부 DB 생성과 `attachment.created` 이벤트도 변환 후에 발생한다.
- `/f/[attachmentId]`는 DB의 저장 경로를 찾아 권한 검사 후 제공한다.
  썸네일이 없으면 원본 경로로 돌아가는 분기가 이미 있다.
- 파일 응답은 private/no-cache와 파일 크기·수정시간 기반 ETag를 사용한다.
- `server.ts`는 이미 휴지통 정리 등 주기 작업을 실행한다.
- Pad 실시간 이벤트 버스는 현재 단일 프로세스 메모리 기반이다.

## 3. 선택한 방식과 대안

**선택: DB에 지속되는 작업 + 기존 서버의 제한된 백그라운드 실행기.**
새 외부 서비스 없이 재시작 복구를 지원하고 기존 이벤트 버스를 재사용한다.
변환 실행은 요청 응답과 분리하되 이미지 처리 자원 제한을 공유한다.
웹 요청과 CPU·디스크는 여전히 공유하므로 무제한 병렬 처리는 하지 않는다.

다른 방식은 다음 이유로 선택하지 않는다.

- 응답 후 메모리 Promise만 실행: 간단하지만 배포·재시작 시 작업이 소실된다.
- 별도 Redis/워커 서비스: 더 강한 자원 격리가 가능하지만 현재 단일 서버 구조에서는
  새 배포 대상과 프로세스 간 이벤트 전달까지 추가된다. 이번 범위에는 넣지 않는다.

## 4. 업로드와 게시 흐름

1. 기존 인증·권한·속도·첨부 개수 제한을 적용한다.
2. 원본을 임시 경로로 스트리밍 수신하고 실제 형식, 바이트 크기, 이미지 크기를 검사한다.
3. 아래 보안 조건에 맞는 원본 해상도 파일을 UUID 경로에 확정한다.
4. 하나의 DB 트랜잭션에서 Attachment와 이미지 처리 작업을 함께 저장한다.
5. 첨부 ID와 실제 초기 MIME·크기·표시 치수를 응답한다. 클라이언트는 모든 파일의
   수신·저장이 완료되면 기존 마지막 PATCH와 게시 완료 처리를 한다.
6. 백그라운드 실행기가 WebP 본문과 썸네일을 별도 임시 경로에 만든다.
7. 완성된 파일을 확정한 뒤, 현재 작업 소유권·첨부 존재·삭제 상태·원본 경로를 확인하는
   조건부 트랜잭션으로 Attachment의 경로·MIME·크기·치수·표시 버전을 교체한다.
8. 교체 후 실시간 이벤트를 보내고 이전 파일은 지연 정리 작업으로 삭제한다.

DB와 파일시스템 사이의 원자적 트랜잭션은 없으므로 각 단계의 중단을 복구 대상으로 삼는다.
파일 확정 후 DB 저장에 실패하면 요청이 파일을 정리한다. 프로세스 강제 종료로 남은
임시 파일 및 DB 미참조 파일은 업로드 전용 경로와 충분한 유예시간 안에서만 정리한다.

## 5. 원본 우선 제공의 보안 조건

- 허용 형식은 현재 브라우저 인라인 허용 목록인 JPEG/PNG/WebP/GIF 범위를 넓히지 않는다.
  확장자와 `image/*` 여부만으로 허용하지 않고 감지된 실제 형식을 제한한다.
- 기존 최대 4천만 픽셀 및 관리자가 정한 이미지·전체 업로드 용량 제한을 유지한다.
- GPS·촬영 장치·사용자 설명 등이 담긴 EXIF/XMP/IPTC/텍스트 메타데이터를 그대로
  제공하지 않는다. JPEG/PNG/WebP의 구조를 검증하면서 재압축 없이 해당 메타데이터를
  제거할 수 있는 경로를 우선 사용한다.
- 회전 방향은 필요한 값만 보존하거나 안전하게 표현한다. 다른 EXIF 내용을 복사하지 않는다.
  색상 프로파일과 회전·표시 치수의 일관성도 테스트한다.
- 초기 구현에서 안전한 제거를 검증하지 못한 형식·컨테이너·애니메이션은
  기존 동기 재인코딩으로 돌아간다. 따라서 모든 파일의 게시 대기가 없어지는 것은 아니다.
- 메타데이터 처리나 구조 검사 실패 시 원시 파일을 공개하는 우회는 허용하지 않는다.
  잘못된 파일은 거절하고, 정상이나 빠른 경로 미지원 파일만 기존 변환을 사용한다.
- 원본 경로도 기존 `/f/` 권한 검사와 nosniff/CSP를 거친다. 공개 정적 디렉터리에 넣지 않는다.

## 6. 작업 상태와 실행기

새 이미지 처리 작업에는 첨부 ID, 입력 경로, 상태, 시도 횟수, 다음 실행 시각,
임대 토큰·만료 시각, 출력 경로, 정리 대상 경로, 오류 코드와 생성·수정 시각을 저장한다.
첨부에는 교체 시 증가하는 `imageRevision`을 추가한다. 기존 첨부의 기본값은 0이다.

- 단계: `PENDING → PROCESSING → CLEANUP_PENDING → DONE`.
- 일시 실패는 최대 5회, 5초·30초·2분·10분 간격으로 재시도한다.
- 재시도 소진 시 `FAILED`로 두고 안전하게 저장된 초기 이미지는 계속 제공한다.
- 처리 작업은 원자적으로 임대한다. 임대 토큰이 다른 오래된 실행기는 결과를 반영하지 못한다.
  긴 변환은 임대를 갱신하며 재시작 시 만료된 작업을 회수한다.
- 유휴 상태에서 2초 간격으로 확인하고 실행 가능한 개수만 가져온다.
  프로세스 메모리에 대기 작업 전체를 적재하지 않는다.
- 변환 동시성은 기존 이미지 처리 게이트를 공유한다. 새 업로드 요청은 해당 변환 큐에
  진입하지 않아 최적화 대기열이 길어도 정상 파일의 수신·저장은 완료할 수 있다.
- 안전한 지속 대기열에도 상한이 필요하다. 비완료 작업 최대 256개를 DB 잠금과 함께
  확인하고, 초과하면 새 비동기 사진 첨부를 503 및 Retry-After로 거절한다.
  이 경우 임시 파일을 정리하고 화면에는 재시도 가능한 업로드 실패를 표시한다.
- 로그에는 단계·소요시간·재시도 수와 내부 ID만 기록한다. 파일 내용·원본 이름·EXIF는 제외한다.

## 7. 파일 교체·삭제·실패 복구

- 입력 파일을 덮어쓰지 않는다. 두 출력이 모두 확정되기 전에는 DB 경로를 바꾸지 않는다.
- 교체 트랜잭션에서 이전 경로의 정리 작업도 기록한다. 교체 후 프로세스가 죽어도
  이전 파일을 잃어버리거나 미참조 파일이 무기한 남지 않아야 한다.
- 기존 파일은 교체 후 최소 60초 유예하고 제거한다. 유예시간만으로 경합을 해결하지 않는다.
  `/f/`는 파일을 열어 핸들을 확보한 뒤 그 핸들로 stat·스트리밍한다. 교체 직전 조회한
  경로가 사라졌다면 DB를 한 번 다시 읽고 권한 재검사 후 현재 파일을 연다.
- 파일 삭제 실패는 정리 단계만 재시도한다. 재변환하거나 최신 파일을 지우지 않는다.
- 첨부·게시물·섹션·보드 삭제와 변환 완료가 경합하면 삭제가 우선한다.
  삭제된 첨부를 재생성하거나 기존 삭제 상태를 되돌리지 않는다.
- 직접 삭제·관리자 영구 삭제·휴지통 sweep·보드 전체 삭제에서 작업의 입력·출력·이전 파일도
  함께 정리한다. Attachment cascade로 정리 경로를 먼저 잃어버리지 않도록 작업 기록은
  파일 정리가 끝날 때까지 보존한다.
- 작업마다 고유한 출력 경로를 사용한다. 임대를 잃은 실행기는 자신의 출력만 정리한다.
- 기존 이미지 복사/보드 재사용/내보내기는 현재 Attachment가 가리키는 표현을 사용한다.
  진행 중 작업 자체를 복제하지 않으며 초기 파일 복제 시에도 MIME·파일명·치수가 일치해야 한다.

## 8. 화면과 캐시

- 외부 참조의 정본은 계속 `/f/첨부ID`다. 게시물 본문의 링크를 수정하지 않는다.
- 이미지 렌더링에는 `imageRevision`을 반영하는 쿼리를 사용한다. 변환 완료 시
  `attachment.updated`로 MIME·치수·파일 크기·revision을 갱신해 열린 화면에서도 새로 읽는다.
- 카드 이미지뿐 아니라 상세 보기와 본문 삽입 이미지도 동일한 URL 생성 규칙을 사용한다.
- 생성 응답과 변환 이벤트의 순서가 뒤집혀도 더 높은 revision을 낮추지 않도록 병합한다.
- 캐시 재검증과 기존 권한 검사는 유지한다. 다음 조회 시 최신 상태를 DB에서 읽는다.
- 진행 UI는 ‘전송 중’과 ‘저장 확인 중’을 구분한다. 변환 진행률을 업로드 진행률로 표시하지 않는다.
  변환 실패를 이미 완료된 게시물의 게시 실패로 되돌리지 않는다.
- 기존 첨부 부분 실패·재시도·필수 첨부·게시물 승인 흐름은 변경하지 않는다.

## 9. 검증 기준

운영 데이터·실제 사용자 사진을 사용하지 않고 생성한 fixture와 격리된 테스트 DB로 검증한다.

1. 변환 실행을 의도적으로 멈춰도 초기 업로드 응답·게시 완료·이미지 조회가 성공한다.
2. 동시 업로드에서 변환 동시성 제한이 유지되고 게시 완료가 변환 완료 순서에 종속되지 않는다.
3. 잘못된 형식·초과 용량·초과 픽셀·손님 정책 위반이 이전과 같이 거절된다.
4. EXIF GPS/XMP/IPTC/텍스트, 회전 JPEG, PNG, WebP, 애니메이션 및 손상 컨테이너를 확인한다.
5. 성공 교체 후 링크 유지·MIME/파일명 일치·썸네일 전환·revision 역전 방지를 검증한다.
6. 작업 중단·임대 만료·중복 실행·DB 실패·디스크 실패·재시도 소진 시 초기 이미지가 보존된다.
7. 완료 직전 삭제, 보드 삭제, 스트리밍 중 교체, 원본 삭제 실패와 복구를 검증한다.
8. 보드 재사용·복사·내보내기 및 다른 업로드 소비자의 기존 동작을 회귀 검증한다.
9. 타입 검사·린트·관련 회귀 테스트와 격리한 프로덕션 빌드를 실행한다.

## 10. 적용 및 문서

- 새 테이블·필드는 기존 첨부를 변경하지 않는 추가형 마이그레이션으로 작성한다.
- DB 마이그레이션을 먼저 적용하고 새 앱을 실행한다. 실행기와 새 비동기 업로드는
  하나의 기능 설정으로 함께 활성화한다. 롤백 시 해당 설정을 끄면 기존 동기 업로드를 사용한다.
- 롤백 중 남은 초기 이미지는 현재 `/f/`가 지원하는 MIME·경로 구조로 계속 읽을 수 있어야 한다.
  기존 앱만 실행하는 동안 처리가 멈추는 것은 허용하되 파일을 잃어서는 안 된다.
- README, 파일 처리·Pad 첨부 관련 overview, 운영 설정 및 장애 복구 문서를 갱신한다.
- 실제 운영 DB 마이그레이션·배포는 코드 검증 이후 별도 승인 범위다.

이 문서는 구조와 수용 기준에 대한 검토본이다. 승인 후 파일별 구현 계획과 테스트 순서를
작성하며, 현 단계에서는 제품 코드·DB·실행 중 서버를 변경하지 않는다.
